# Log

## 2026-09-16
* **Planning**: Added [the runtime theme switching plan](plans/okf_site_themes_plan.md) after checking whether ahead-of-time Tailwind blocks visitor-selectable themes. It does not: of `site.css`'s 536 declarations, 62 carry a color literal and 51 of those sit in the three token blocks, the rest being Tailwind's own `--color-violet-300/400`, two preflight `#0000` form-control backgrounds, and one alpha-black search-panel shadow - so every semantic color already resolves through `var(--token)` and a theme is a set of *values*, which custom properties re-resolve at runtime, not a set of *rules*, which is what the AOT build fixes. The plan splits today's `.dark`/`.light` class into two attributes on `<html>`: `data-scheme` (light/dark base palette, `color-scheme`, shiki side, mermaid base, sun/moon glyph) and `data-theme` (palette overrides), which keeps no-JS and first paint exactly as they are (neither attribute = today's media-query behavior), lets bundle themes be partial (the scheme block seeds what they omit), and means the derived light/dark ladders need no per-theme CSS. Catalog is compiled into `tailwind.css` (`auto`/`light`/`dark` plus new `sepia`/`contrast`) with a `SITE_CSS` selector test guarding drift against the Rust `BUILTIN_THEMES` table; bundles extend it through `site.themes` in `.okf/config.yaml`, emitted as a generated `assets/theme.css` on the `fonts.css` precedent (opt-in, constructed not interpolated, closed token-key set and closed color grammar). The two-state button becomes a keyboard-operable menu; `okf-theme` keeps its shape, so stored `light`/`dark` values remain valid ids and need no migration. Out of scope in v1: per-theme shiki palettes (possible - shiki emits `--shiki-<key>` for any theme - but adding one is a manual esbuild re-bundle of a 9.6 MB asset).

## 2026-09-15
* **Implementation**: Shipped per-bundle site configuration and fonts per [the plan](plans/okf_site_fonts_plan.md), all five milestones, and promoted the mechanism to [its own decision record](decisions/okf_bundle_tool_config.md). **Typography tokens**: `tailwind.css` gained `--font-body`/`--font-code`; `body`'s `font:` shorthand split into `font-size`/`line-height`/`font-family` (a `var()` that fails to substitute invalidates its whole declaration, which would take the size down with the family), and `code`/`pre` resolve the code token explicitly instead of inheriting Tailwind's preflight `--default-mono-font-family`. Both defaults restate the previously computed values, so `site.css` recompiled with one changed line and no visual change. **Config**: new `crates/okf-web/src/config.rs` reads `.okf/config.yaml` with `okf_core::yaml` — zero new dependencies — into `SiteConfig { title, fonts, notes }`. `.okf/` is invisible to every walker (the loader collects `*.md` only), so config and font binaries never become concepts. Content stays permissive, config is strict: a missing file is the default config (output byte-identical to before), a malformed one reports the YAML line, an unknown key names the section's known keys, and an unknown *section* is only noted (`SiteSummary::notes`, printed by the CLI) so a config written for a newer okf degrades rather than breaks. `SiteError::Config` is distinct from `Io`; title precedence is `--title` > `site.title` > `DEFAULT_SITE_TITLE`, merged in `generate()`, and the now-misleading `SiteOptions::effective_title` was removed. **Fonts**: `site.fonts.body`/`code` become a `:root` token override and `site.fonts.files` become `@font-face` rules in a generated `assets/fonts.css`, linked after the inline `<style>` with the per-page `{prefix}` and written only when a bundle configures fonts; named files are copied from `.okf/fonts/` to `assets/fonts/` (deduplicated, missing file → config error) and the `url()` is stylesheet-relative so one href works at every depth and over `file://`. CSS is constructed, never interpolated — family lists re-emitted with generic keywords bare and names quoted after a charset check, weights numeric, styles a closed vocabulary, file names flat ASCII so `../` is a parse error — and the mermaid boot now reads the computed `--font-body` for `fontFamily`, so diagrams follow the prose. `render.rs` grew a `SiteChrome` struct rather than a sixth positional argument to `write_page`. Verified: 48 tests in okf-web (10 new), no-config output diffed byte-identical to a pre-change build except the intended mermaid `fontFamily` read, and a browser check over `file://` of this KB with a serif body plus two self-hosted faces — `document.fonts` reports both loaded, prose/nav/header/shiki blocks and diagram labels all resolve the configured families, light and dark both clean, no console messages.
* **Fix**: `okf site` now reports the configuration it read, after a real build looked exactly like the feature was broken. A config that never reaches the generator — a `.okf/` one directory above the bundle root passed to `okf site`, or an installed `okf` predating the feature — produced output identical to having no config, and a family name that the viewer's machine does not have (`MapleMono` where the installed family is `Maple Mono`) falls back silently by CSS design. `SiteConfig` now carries the `path` it was read from, `SiteConfig::settings()` lists the `site:` keys that supplied something, and `SiteSummary` reports both (`config`, `config_settings`) so the CLI prints `read docs/.okf/config.yaml (title, fonts.body, fonts.code)` — a line whose *absence* is the diagnosis. `--title` overriding a configured `site.title` is noted too. Font *availability* stays a viewer-side fact the generator cannot assert: the deterministic answer is `fonts.files`, which the READMEs now say explicitly.
* **Implementation**: `okf site`'s nav gained collapsible submenus and the site's links went violet. Each directory row in the nav tree is now a `.dir-row` (the existing `<a class="dir">` plus a caret `<button class="dir-toggle">` on the far right) inside an `<li data-dir="path">`; the button's `aria-expanded` is the *only* collapse state — `site.css` hides `li:has(> .dir-row > .dir-toggle[aria-expanded="false"]) > ul` and rotates the single chevron glyph a quarter turn to point right — so the accessible state cannot drift from the rendered one. Pages ship every submenu expanded (the default, and what no-JS gets); `NAV_SUBMENU_BOOT` applies the persisted closed set and writes it back on click as `okf-nav-closed`, a JSON array of directory paths that is removed when nothing is closed, re-read before each write so two tabs merge instead of clobber. Flash-free like the theme: the nav does not exist when the `<head>` boot runs, so `THEME_BOOT` injects a `#site-nav li[data-dir=…]` stylesheet (paths through `CSS.escape`, an unquoted attribute value being an identifier, so a hand-written key cannot inject rules) mirroring those rules, which the submenu boot drops once aria is authoritative. Link color moved from blue-700/blue-300 to violet-700/violet-300 (`--link`, the only token touched — nav labels stay body ink). Verified in a browser over both themes: carets flip, submenus hide, state survives navigation, and the injected style alone collapses a closed submenu while `aria-expanded` still reads `true`.
* **Fix**: Rust code blocks rendered unhighlighted whenever the fence carried rustdoc directives. The fence info string was split on spaces only in three places (`Intercept::is_mermaid`, the `has_shiki` gate, and the writer's class), so ` ```rust,no_run ` — the idiomatic Rust form, and the one this repo's own README uses — emitted `<code class="md-code language-rust,no_run">`; the shiki boot harvested `rust,no_run`, found no such grammar in the bundled map, and left the plain `<pre>`. Shiki was never language-limited: the vendored bundle carries every shiki language with the Oniguruma engine precisely so `rust`/`toml`/`go` work. Fixed with one normalizer, `markdown::fence_lang` — the leading identifier run (`-`, `+`, `#`, `_` kept, since `objective-c`, `c++`, and `c#` are real ids) — used by all three call sites, so directives in either shape (`rust,no_run`, `js {1,3}`, `python title="x"`) are dropped from the emitted language and the plain-language list is matched case-insensitively. Also fixed a related swap artifact: shiki's replacement `<pre>` carries no `md-code` on its `<code>`, so highlighted blocks rendered at 15px against 13.5px for unhighlighted ones and popped when the highlight landed; `tailwind.css` now sizes `.md-pre code` instead of relying on the class. Verified in a browser over `file://` and http: all three fence shapes highlight with four distinct token colors, and code size is stable across the swap.

## 2026-09-13

Follows the mermaid precedent exactly: rendered client-side (highlighting at build time would put a JS runtime in the build chain, per the [decision record](decisions/okf_web_static_site.md)), loaded only on pages with language-tagged fences, escaped source kept as the no-JS fallback. One dual-theme render (`defaultColor: false`): token colors ship as `--shiki-light`/`--shiki-dark` CSS variables resolved by the site stylesheet under `.dark`/`.light`, so theme toggling is free (no re-render, unlike mermaid). `okf site` summary now reports code pages; NOTICE/vendor README/okf-web docs updated.
